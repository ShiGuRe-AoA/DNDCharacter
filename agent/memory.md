## 1. 项目概况

这是一个面向 D&D 玩家使用的网页角色卡工具。当前以静态
HTML、CSS、JavaScript 实现，并部署在 Cloudflare Pages。

长期目标是将其升级为完整的多页面角色管理网站：

-   网站主页。
-   用户角色列表。
-   保留现有角色卡编辑器。
-   创建、编辑、复制、删除多张角色卡。
-   本地持久化保存。
-   后续增加用户注册 / 登录。
-   后续增加云端角色卡存储与同步。
-   延续 Character JSON 作为统一数据契约。
-   保留 Foundry VTT（FVTT）导出能力。

用户当前本地项目目录：

``` text
D:\\shigure-aoa网页\\shigure-aoa_website
```

用户希望后续直接在这个真实项目目录上继续开发。

**访问限制：** 普通聊天不能仅凭 Windows 本地路径直接读取 D
盘文件。需要通过 ChatGPT 桌面应用中可用的 Work /
本地文件工作流授权访问，或由用户上传整个项目
ZIP。开始修改前先检查目录和真实文件，不要根据聊天中曾生成的文件名猜测项目当前状态。

## 2. 已确定的技术路线

### 2.1 当前部署方式

-   使用 Cloudflare Pages。
-   当前采用控制台直接上传 HTML 文件 / 文件夹的方式部署。
-   第一阶段继续使用原生 HTML + CSS + JavaScript。
-   当前不强制引入 Vue、React 或 Node.js。
-   Node.js 仅在未来需要本地构建工具、Wrangler 或自动化测试时再考虑。
-   Vue 可以作为未来前端复杂度进一步增加时的可选重构方向，不是当前前提。
-   不要擅自把部署流程改成必须依赖 GitHub 的方式。

### 2.2 Cloudflare 后续后端方案

未来可以继续留在 Cloudflare 生态：

-   Cloudflare Pages：静态前端。
-   Pages Functions 或独立 Cloudflare Worker：后端 API。
-   Cloudflare D1：用户资料和角色卡数据。
-   Cloudflare R2：角色立绘和附件。
-   后续选择安全的身份认证方案。

注意：控制台直接拖拽上传静态文件，不会自动部署 Pages
Functions。接入后端时需要使用支持 Functions 的部署方式（例如
Wrangler）或单独部署 Worker
API。不要把数据库密钥或服务端密钥放在浏览器代码中。

### 2.3 第一阶段存储方案

第一版多角色管理建议使用 IndexedDB：

-   支持同一浏览器内保存多张角色卡。
-   适合保存结构化 JSON 和较大的角色数据。
-   不需要后端或用户注册。
-   必须保留 JSON 文件导入 / 导出作为备份和迁移途径。

IndexedDB
仅属于当前浏览器、当前网站源。换设备或清理网站数据可能导致本地存档不可用。Cloudflare
预览域名与正式域名的 IndexedDB 也不会自动共享。

## 3. 核心数据架构：JSON-First

**Character JSON 是角色卡的标准数据契约（Canonical Data
Model），而不只是导入 / 导出文件格式。**

所有模块围绕同一份 JSON 数据工作：

-   角色卡编辑器：读取和修改 Character JSON。
-   本地存储：保存完整 Character JSON。
-   云端数据库：保存完整 Character JSON。
-   JSON 文件：离线备份、导入、导出和分享。
-   FVTT 导出器：将 Character JSON 转换为 Foundry 原生 Actor JSON。
-   未来其他客户端：继续使用同一份数据契约。

不要让 UI
或数据库成为角色卡数据的唯一真实来源。前端框架和存储方式可以替换，而
Character JSON 契约应保持稳定。

### 3.1 Character JSON v9

聊天中已经制定并使用过 Character JSON v9 的语义化方向。语义字段示例：

  -------------------------------------------------------------------------------------------------------------------
  数据                                语义路径示例
  ----------------------------------- -------------------------------------------------------------------------------
  角色名称                            `identity.name`

  职业文本                            `identity.classText`

  六维属性                            `abilities.str`、`abilities.dex` 等

  当前生命值                          `combat.hitPoints.current`

  护甲等级                            `combat.armorClass`

  装备 / 金钱等资源                   `resources.*`

  人物档案                            `profile.*`

  特性条目                            `featureEntries.race`、`featureEntries.classFeatures`、`featureEntries.other`

  法术书                              `spellbook.*`

  魔宠 / 召唤物                       `summons`

  立绘等资源                          `assets.*`
  -------------------------------------------------------------------------------------------------------------------

以上是语义设计示例。实际开发必须以当前项目中的 v9
Schema、模板和序列化代码为准，不要仅凭此表重建字段。

### 3.2 富文本

既定方向：

-   普通字段保存纯文本，便于搜索、计算和其他程序读取。
-   富文本格式单独保存，例如通过 `formattedText` 使用语义路径索引。

示例：

``` json
{
  "profile": {
    "backstory": "这是一段加粗的故事"
  },
  "formattedText": {
    "profile.backstory": "<strong>这是一段加粗的故事</strong>"
  }
}
```

具体字段应遵循当前 v9 Schema。不要在迁移时丢失 Ctrl+B
加粗格式或粘贴内容。

### 3.3 版本迁移

-   JSON 应带有 `schema`、`version`、`sheetId` 等契约元信息（以当前
    Schema 为准）。
-   旧版编号字段（例如 `field-001`、`field-046`）需要保留读取迁移能力。
-   旧版特性文本框迁移规则：整段旧文本作为一个新特性条目的描述，名称和次数留空，不自动拆分。
-   未知扩展字段应尽可能保留，避免新旧版本往返时误删扩展数据。
-   所有导入数据先迁移、校验到当前版本，再交给编辑器。
-   不要因页面布局变化而让字段编号重新对应到其他内容。

## 4. 现有角色卡功能与历史需求

开始修改前，应检查当前 HTML
确认哪些功能已经在真实版本中实现。以下是聊天中提到的既有功能和设计要求。

### 4.1 基本角色数据

-   身份信息：角色名称、职业、种族、背景、玩家名称、阵营、经验值、激励等。
-   六维属性与调整值自动计算。
-   护甲等级、速度、生命值等战斗数据。
-   技能熟练 / 专精、豁免熟练。
-   攻击数据。
-   金钱、装备、物品。
-   人物档案：年龄、身高、体重、外貌、背景故事、个性、理想、羁绊、缺点等。

### 4.2 特性条目

特性已从单一大文本框改为多条目模式，类别包括：

-   种族特质。
-   职业特性。
-   专长与其他特性。

每条目包含名称、可用次数 /
最大可用次数、描述、折叠状态和使用次数记录。折叠后显示名称和使用次数圆圈。类别底部提供「添加条目」和「恢复所有使用次数」操作。

旧版迁移规则：整段旧文本作为单个条目的描述，名称和使用次数为空，玩家自行整理，不自动拆分。

### 4.3 特性使用次数按钮状态（最近明确需求）

最终视觉约定：

-   **实心圆 = 可用次数。**
-   **空心圆 = 已使用次数。**
-   点击实心圆变为空心，剩余可用次数减少。
-   点击空心圆变为实心，剩余可用次数增加。
-   手动修改可用次数时，圆圈状态同步变化。
-   「恢复所有使用次数」将所有圆圈恢复实心，并把可用次数恢复到最大值。
-   不使用技能熟练 / 专精的三态切换模式。
-   圆圈尺寸和基本视觉样式与技能 / 豁免检定按钮保持一致。
-   需确认 JSON 中 `used` / 剩余次数的语义与 UI
    一致，避免反转视觉时破坏旧存档数据。

### 4.4 魔宠 / 召唤物

支持创建多个召唤物角色卡，垂直排列，可折叠。字段包括：

-   名字。
-   当前 / 最大生命值。
-   护甲等级。
-   速度。
-   六维属性及对应调整值。
-   技能（自由输入，不全量枚举）。
-   伤害免疫。
-   状态免疫。
-   感官。
-   语言。
-   熟练加值。
-   能力（较大的可扩展输入框）。
-   动作（较大的可扩展输入框）。

不应用自动角色卡功能。折叠后只显示名字和生命值 / 最大生命值。

### 4.5 法术书与法术位

-   法术书有法术输入和准备状态。
-   法术输入与准备选择曾发生冲突，需要保留修复。
-   每个法术环位有拥有数量输入框。
-   输入数量后生成对应数量的可点击圆圈，表示法术位使用状态。
-   圆圈可点击切换使用 / 未使用。
-   需保留 JSON 保存与导入。

### 4.6 富文本与文本框

-   文字输入框支持 Ctrl+B 加粗 / 取消加粗。
-   粘贴富文本时曾出现异常额外换行，已有修复需求。
-   输入框默认最小高度应尽量小，并根据内容自动扩展。
-   旧版富文本格式和 JSON 兼容性需要保留。

### 4.7 角色立绘与 PDF

-   角色立绘上传 / 显示功能在无后端情况下通过浏览器本地实现。
-   PDF 导出需要匹配新版角色卡排版。
-   尽量避免单个信息框跨页拆分。
-   曾修复首页核心排版问题。
-   这些功能在迁移到多页面时必须做回归测试。

### 4.8 FVTT 导出

已有 FVTT 导出功能设计：

-   从网页角色卡导出 Foundry VTT 原生 Actor JSON。
-   写入角色基本信息、六维、技能熟练 / 专精、豁免熟练。
-   尝试根据中文职业名称匹配 D&D 职业，并创建职业 Item、填入职业等级。
-   特性条目创建独立特性物品，写入名称、描述、可用次数。
-   复杂装备、法术活动、召唤物等由用户在 FVTT 内调整。
-   豁免在 FVTT 原生模型中不支持专精时，应提示并降级处理。
-   真实导入兼容性需要结合用户实际 FVTT 核心与 D&D 5e
    系统版本验证。结构测试不等于真实 FVTT 导入测试。

## 5. 最近增加的自动计算需求

### 5.1 施法属性自动卡

填写职业后，施法属性自动按职业主属性填写默认值，但允许用户手动覆写。

常见 D&D 5e 默认映射：

  职业              默认施法属性
  ----------------- --------------
  法师              智力
  奇械师            智力
  牧师              感知
  德鲁伊            感知
  游侠              感知
  吟游诗人          魅力
  圣武士            魅力
  术士              魅力
  邪术师 / 契术师   魅力

多职业和子职业可能存在特殊施法来源，因此自动映射只是默认值，不能阻止用户手动覆写。

施法属性字段无论自动填写还是手动覆写，只要能匹配六大属性名称或缩写，就读取对应属性调整值。

法术豁免 DC：

``` text
8 + 施法属性调整值 + 熟练加值 + 法术豁免 DC 修正
```

法术攻击加值：

``` text
施法属性调整值 + 熟练加值 + 额外法术攻击修正
```

DC
和攻击加值本身也允许用户手动覆写。清除覆写后恢复自动计算。自动值与手动值应明确区分，避免自动更新覆盖用户明确输入的覆写。

### 5.2 熟练加值自动计算

按角色总等级自动填写默认熟练加值，允许手动覆写。

  角色总等级     熟练加值
  ------------ ----------
  1--4                 +2
  5--8                 +3
  9--12                +4
  13--16               +5
  17--20               +6

多职业时总等级应为所有职业等级之和。手动覆写应有明确状态，不应因等级变化被自动覆盖。

### 5.3 侧边栏额外修正

新增四个独立手动输入框：

-   技能检定加值。
-   豁免检定加值。
-   法术豁免 DC 加值。
-   额外法术攻击加值。

这些修正影响对应自动计算结果，并需要保存到 Character JSON。

### 5.4 万事通（Jack of All Trades）

**万事通只影响不具有熟练的技能检定，不影响已经熟练或专精的技能，也不影响豁免检定。**

D&D 5e
常见计算为熟练加值的一半向下取整。应用该修正时，必须检查技能熟练等级为
0。

## 7. 本地存储抽象

推荐 IndexedDB，不建议用 localStorage 保存完整角色数据。

统一接口示例：

``` javascript
const CharacterDB = {
  async create(data) {},
  async get(id) {},
  async getAll() {},
  async update(id, data) {},
  async delete(id) {}
};
```

建议存储记录：

``` javascript
{
  id: "角色UUID",
  name: "露米娅·四叶草",
  schemaVersion: 9,
  createdAt: "ISO-8601时间",
  updatedAt: "ISO-8601时间",
  data: {
    // 完整 Character JSON v9
  }
}
```

设计原则：

-   UUID 是存档主键，不使用角色名称作为主键。
-   角色名称可以重复。
-   `data` 保存完整 Character JSON。
-   `name`、`updatedAt` 等可作为列表展示元数据。
-   保存前验证 / 迁移到当前 JSON 版本。
-   自动保存应防抖，避免每次键入都立即写入。
-   防止页面切换或关闭时未完成的写入丢失。
-   IndexedDB 本地数据与云端数据未来通过 Repository / Adapter 抽象隔离。

## 8. 云端用户系统与数据库（后续阶段）

第一版不必立即实现用户注册和云端存储。

后续建议 Cloudflare 生态：

-   Cloudflare Pages：静态前端。
-   Pages Functions 或 Worker：API。
-   D1：用户关联的角色卡数据。
-   R2：立绘与附件。

角色表可采用以下方向：

``` sql
CREATE TABLE characters (
    id TEXT PRIMARY KEY,
    owner_id TEXT NOT NULL,
    name TEXT NOT NULL,
    schema_version INTEGER NOT NULL DEFAULT 9,
    data TEXT NOT NULL,
    created_at TEXT NOT NULL,
    updated_at TEXT NOT NULL
);
```

安全要求：

-   用户显示 ID 不能作为权限凭证。
-   必须有真正的身份认证。
-   服务端从认证会话取得用户身份。
-   服务端验证角色归属后才能读取、更新、删除。
-   不信任客户端传入的 `owner_id`。
-   不在前端暴露数据库密钥或服务端密钥。
-   云端同步要考虑并发编辑和冲突处理。
-   保留本地备份和 JSON 导出。

## 9. 手机端体验与全屏

用户希望手机浏览器中有全屏体验。已讨论两种方案：

1.  Fullscreen API：由用户点击按钮触发；Android 浏览器通常支持，iOS
    Safari 对普通网页元素的支持有限。
2.  PWA：添加 Web App
    Manifest、应用图标和主屏幕安装指引。通过主屏幕启动时可获得更接近 App
    的独立窗口体验。

建议后续增加：

-   移动端全屏按钮。
-   检测 `document.fullscreenElement`。
-   浏览器不支持时提示添加到主屏幕。
-   PWA Manifest。
-   安全区域适配，避免刘海和底部手势区域遮挡控件。

这不是当前多页面第一阶段的阻塞项。
